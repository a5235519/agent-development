# 多模态无限节点画布全面评估

> 最新结论：V0.7 已完成工程、画布、资产、插件、运行和版本的交互闭环。当前客观验收、P0 阻塞项及后端接入决策见 [V0.8-客观验收与后端接入决策.md](./V0.8-客观验收与后端接入决策.md)。本文主体保留 V0.1/V0.2 的历史基线，用于对照能力演进。

> 评估对象：`infinite-multimodal-canvas` Harness V0.1  
> 评估范围：节点库能力模型、组合完整性、节点卡信息、无限画布空间布局、模式与面板关系  
> 评估原则：只判断用户当前能否完成任务，不以代码量、页面数量或视觉完成度替代可用性。

> V0.2 执行状态：已完成节点库七组重构、Prompt 合并、脚本/视频/转换/控制/人工/Gate 节点补充、五模板质量闭环、Inspector 按需浮层、节点库收起、70% 最低缩放、DAG 分层布局和本地文件内嵌数据。本文主体保留 V0.1 的客观基线，用于继续核对尚未完成项。

## 1. 总体结论

当前 Harness 已经验证了五种多模态组合的最小概念，但仍属于“模板演示型节点画布”，尚未成为可扩展的多模态 Agent 编排工具。

综合成熟度建议按 **5.1/10** 管理：

| 维度 | 评分 | 判断 |
|---|---:|---|
| 五类基础组合覆盖 | 8/10 | 文生图、图生图、文生视频、图生视频、图文插件均有模板 |
| 节点职责清晰度 | 5/10 | 部分节点职责重复，抽象层级混杂 |
| 端口类型体系 | 7/10 | 基础媒体类型明确，但缺转换、控制和插件动态端口 |
| 复杂流程可组合性 | 3/10 | 缺少选择、合并、批处理、条件、审核与 Gate |
| 质量闭环 | 3/10 | Validator 存在，但模板未使用，也没有 Gate 消费报告 |
| 插件扩展模型 | 4/10 | 当前通用插件节点实际是固定三输入模板，不是真正动态插件 |
| 节点库发现效率 | 5/10 | 有搜索和分类，但分类碎片化，缺少用途、来源与兼容信息 |
| 画布空间利用 | 4/10 | 固定双侧栏压缩画布，默认缩放导致内容不可读 |
| 无限画布真实性 | 4/10 | 有缩放和移动，但世界尺寸固定，小地图与自动布局不真实 |
| 模式与面板协作 | 4/10 | 模式可切换，但 Inspector 与右键操作没有彻底锁定 |

最关键的产品判断是：

> 下一步不应继续简单增加“某某生成”节点，而应先重构节点分层、补齐流程控制节点，并重新组织画布空间。

## 2. 当前节点库逐项评估

## 2.1 输入、提示和资产

| 当前节点 | 作用 | 判断 | 建议 |
|---|---|---|---|
| 文本输入 | 产生 `text.plain` | 与 Prompt 编排组合后才能进入生成器，基础流程被拆得过细 | 普通用户入口合并为“Prompt”；保留纯文本节点供高级映射使用 |
| Prompt 编排 | `text.plain → text.prompt` | 类型转换合理，但每个最小模板都必须多放一个节点，增加认知负担 | 改为“Prompt”主节点；模板、变量、引用在 Inspector 中配置 |
| 图片资产 | 输出单图 | 适合首帧、尾帧、蒙版之外的单图角色 | 保留，增加资产角色、版本固定和来源标识 |
| 多图片资产集合 | 输出图片集合 | 是图生图与多模态插件的核心素材节点 | 保留，必须补主参考图、角色、顺序、数量和版本信息 |
| 蒙版 | 输出单蒙版 | 必要但低频，不应与普通图片资产同等突出 | 放入“高级/局部编辑”或由图生图节点上下文推荐 |
| 生成配置 | 输出 `config.json` | 把比例、数量、时长等常用字段节点化，会造成画布碎片 | 默认收进生成节点 Inspector；仅“共享配置/变量化”时创建独立节点 |

### 核心问题

当前最小文生图链路为：

```text
文本输入 → Prompt 编排 → 文生图 → 图片画廊
```

对普通用户而言，更自然的最小链路应为：

```text
Prompt → 文生图 → 图片结果
```

只有在需要脚本拆分、变量复用、模板合成或 Agent 生成 Prompt 时，才显示额外的文本处理节点。

## 2.2 生成节点

| 当前节点 | 作用 | 判断 | 建议 |
|---|---|---|---|
| 文生图 | Prompt → 图片集合 | 职责清晰 | 保留；模型、比例、数量、种子属于 Inspector |
| 图生图 | 图片集合 + Prompt + 可选蒙版 → 图片集合 | 职责基本清晰 | 保留；主图、角色参考、风格参考不能只依赖集合顺序 |
| 文生视频 | Prompt → 视频集合 | 职责清晰 | 保留；需要明确时长、比例、音频和首帧策略 |
| 图生视频 | 首帧 + 可选尾帧 + Prompt → 视频集合 | 当前设计最合理，资产角色明确 | 保留；增加多参考图/一致性参考的扩展端口 |

### 生成节点共同缺口

- 节点库未显示具体模型能力和可用状态。
- `executorRef` 是占位路由，但界面看起来像已经安装的真实插件。
- 节点实例无法切换 NodeDefinition 版本。
- 缺少成本、时长、分辨率、并发和区域能力摘要。
- 缺少批处理语义，`many` 端口没有说明是一组输入还是逐项运行。
- 输出始终是 collection，单结果和多候选的差异没有被用户明确感知。

建议生成节点卡固定显示：

1. 模型/插件与版本；
2. 输入就绪度；
3. 核心参数；
4. 输出数量与媒体规格；
5. 运行状态与最近结果；
6. 成本或额度提示。

## 2.3 多模态插件节点

当前 `图 + 文 + 插件` 节点声明：

```text
image.collection + text.prompt + config.json
→ artifact.collection
```

它只能表达一种固定插件形态，不能代表“插件系统”。不同插件可能需要：

- 单图、首帧、尾帧或多组图片；
- 脚本、Prompt、结构化 JSON 或音频；
- 图片、视频、脚本、3D、报告等不同输出；
- 一个 operation 或多个 operation；
- 动态字段、审批权限和特定 Runner。

因此应取消节点库中的固定“图 + 文 + 插件”通用节点，改为：

> 管理端发布一个 PluginVersion 后，根据它的 NodeDefinition 动态生成具体插件节点。

节点库应显示具体名称，例如：

- 分镜草图生成；
- 角色一致性检查；
- Seedance 镜头生成；
- 图片背景移除；
- 脚本镜号拆分。

每个插件节点使用自己的 typed port，而不是统一退化成 `artifact.collection`。否则插件产物无法直接连接图片画廊、视频校验器或其他强类型节点。

## 2.4 校验与结果节点

| 当前节点 | 作用 | 当前问题 | 建议 |
|---|---|---|---|
| 图片校验 | 图片集合 → 校验报告 | 五个模板均未使用；报告没有消费者 | 保留，并新增 Gate/问题节点消费报告 |
| 视频校验 | 视频集合 → 校验报告 | 同上 | 保留，并支持技术、内容、连续性多种规则集 |
| 图片画廊 | 图片集合的查看终点 | 更像 UI 面板，不完全是执行节点 | 改名“图片结果/图片集合”，承担版本与审阅状态 |
| 视频画廊 | 视频集合的查看终点 | 同上 | 改名“视频结果/视频集合” |
| 产物集合 | 异构产物终点 | 与强类型画廊割裂，类型过宽 | 仅作为交付包或插件原始输出；优先保留强类型输出 |

当前质量链路并未闭环。正确结构应为：

```text
生成器 ─→ 结果集合 ─→ 后续生产
   └────→ Validator ─→ Gate ─→ 通过/阻塞/人工审核
```

Validator 的报告必须被 Gate、问题中心或人工审核消费，否则只是一个无法影响流程的旁路节点。

HARNESS 规范中已经提到部分处理节点，但实际目录未实现。以下不是“增强功能”，而是复杂组合成立的前提。

## 3.1 P0 必须补齐

| 节点 | 输入 → 输出 | 为什么需要 |
|---|---|---|
| Prompt | 文本、变量、引用 → `text.prompt` | 取代“文本输入 + Prompt 编排”的默认双节点 |
| 脚本/文档资产 | 文件或文本 → `document.script` | 支撑真实柠萌旅行记脚本和镜号生产 |
| 视频资产 | 视频 → `video.single/collection` | 支撑视频再处理、验证与插件输入 |

| 合并集合 | 多个 single/collection → collection | 组合多来源参考资产 |

## 4. 推荐的节点库重组

当前分类为输入、提示、资产、配置、生成、插件、校验、结果。分类过细且多数组只有一两个节点，用户需要滚动理解技术分类。

建议改成面向任务的七组：

| 新分组 | 内容 |
|---|---|
| 素材与内容 | Prompt、脚本/文档、图片、图片集合、视频、蒙版 |
| 生成 | 文生图、图生图、文生视频、图生视频 |
| 处理与转换 | 选择、合并、拆分、批处理、抽帧、字段映射 |
| 插件与 Agent | 已发布的具体插件节点、Skill Adapter、Codex/Agent 节点 |
| 流程控制 | 条件、Join、循环/批次、缓存、错误处理 |
| 校验与人工 | 图片/视频校验、人工审核、Gate |
| 结果与交付 | 图片结果、视频结果、报告、交付包、发布 |

节点库顶部应从一个模板下拉框改为标签结构：

```text
[节点] [模板] [插件] [最近使用] [收藏]
```

### 节点库卡片最少信息

- 名称与用途，而不仅是输入/输出数量；
- 输入/输出类型图标；
- 来源：内置、插件、Skill Adapter、团队模板；
- 版本与安装状态；
- 是否需要模型、外网、文件或审批权限；
- 与当前拖出端口是否兼容；
- 最近使用与收藏。

从端口拖到空白处时，节点库只显示兼容节点，不应让用户重新搜索全部目录。

## 5. 当前画布布局评估

## 5.1 当前布局

```text
顶部 56
左节点库 268 | 中央画布 | 右 Inspector 334
                       └─ 底部运行抽屉 280
```

### 优点

- 左侧创建、中间编排、右侧配置的心智模型清楚。
- 运行抽屉与画布在同一上下文中。
- 深色网格适合长时间编辑。
- 节点内有媒体缩略图，符合多模态工作场景。

### 核心问题

1. **中央画布过窄**：1280 宽度下，扣除 268 + 334 后只剩约 678 像素。
2. **默认缩放不可读**：五节点模板适配后约为 45%，节点文字和端口接近不可读。
3. **两侧栏始终占位**：没有选择节点时，右栏仍占 334 像素。
4. **运行抽屉再次压缩画布**：打开后可见画布高度显著减少，没有保持当前焦点。
5. **固定世界不是真无限画布**：世界尺寸写死为 5000 × 3200。
6. **小地图为装饰**：没有真实投影节点和当前视口，也不能导航。
7. **自动布局不理解拓扑**：只是按每行三列排列，可能增加交叉线。
8. **连线位置依赖估算**：节点高度、端口数量或样式变化后容易错位。
9. **平移方式不符合常规预期**：目前依赖 Alt 或中键，缺少空白拖动与 Space + 拖动。
10. **模式只改变视觉**：Inspector 字段、键盘删除和部分右键动作未完全按模式锁定。

## 5.2 推荐的响应式工作区

### 设计模式

```text
┌ 顶栏：工程 / 草稿 / 模式 / 保存 / 运行 ┐
├ 节点库 240 ┬──────── 画布 ────────┬ Inspector 360（按需）┤
│ 可收起/浮层 │                      │ 未选择时完全隐藏      │
└────────────┴── 状态条/问题摘要 ───┴─────────────────────┘
```

- 画布可用宽度应优先保证至少 800 像素。
- 1440 以下只允许一个侧栏固定占位，另一个使用浮层。
- 右侧 Inspector 未选择时不占空间。
- 节点库拖入节点后可自动收窄为图标栏。

### 运行模式

```text
┌ 顶栏：版本锁定 / 执行范围 / 取消 ┐
├──────────── 只读画布 ───────────┤
├ 底部调试抽屉：总览/节点/事件/问题/收据 ┤
```

- 隐藏节点库；
- Inspector 改为运行节点详情；
- 活动节点自动保持在视口中，但不强制跳动；
- 抽屉支持 120/280/全屏三档高度。

### 审阅模式

```text
┌ 顶栏：运行版本 / Gate / 修复草稿 ┐
├ 流程缩略图或问题导航 ┬ 资产全屏查看器 ┬ 元数据/评论 ┤
```

- 不应继续以完整节点画布为唯一主视图；
- 图片、视频、脚本和前后镜需要占据主要空间；
- 可从资产或问题回到对应节点。

## 5.3 推荐的画布拓扑布局

多模态流程默认从左到右，按语义阶段形成泳道：

```text
素材与内容 → 处理/Prompt → 生成/插件 → 校验/人工 → 结果/交付
```

布局规则：

- 同一阶段位于同一纵向层；
- 多输入节点靠近输入的几何中心；
- Validator 与主输出并行，而不是强行串在所有结果之前；
- Gate 位于 Validator/人工审核之后；
- 批处理和分支沿纵向展开；
- Frame 表示业务子流程，如“角色资产”“S01–S19 分镜”“视频交付”；
- 自动布局使用 DAG 分层和端口顺序，减少交叉线；
- 用户拖动后的节点位置默认受保护，自动布局只处理未锁定节点。

## 5.4 节点卡密度

当前所有节点使用近似相同的 286 像素宽卡片，但内容高度差异较大。建议三种密度：

| 密度 | 用途 | 内容 |
|---|---|---|
| Compact | 大图导航 | 名称、状态、输入输出就绪度 |
| Standard | 默认编辑 | 关键参数、最多 4 个缩略图、主操作 |
| Expanded | 临时展开 | 运行进度、错误和更多预览；不能替代 Inspector |

默认缩放应保持 70%–100% 可读；“适配全图”只用于导航，不应成为进入模板后的默认长期视图。

## 6. 必须立即修正的交互真实性问题

| 问题 | 当前表现 | 修正要求 |
|---|---|---|
| `file://` 打开失败 | JSON `fetch` 可能被本地安全策略拦截 | 只提供 HTTP 入口，或将目录打包为可直接加载资源 |
| Inspector 假标签 | 输入、输出、运行、问题、历史按钮没有内容切换 | 未实现前禁用或补齐真实面板 |
| 右键“粘贴”假操作 | 菜单存在但没有实现命令 | 实现 Clipboard 图数据或暂时移除 |
| 模板菜单不完整 | “载入组合模板”仅聚焦下拉框 | 打开真正模板选择面板 |
| 模式未完全锁定 | 运行/审阅模式仍可能改配置或删除 | 在所有写操作入口统一执行权限守卫 |
| 小地图为装饰 | 不映射节点和视口 | 实现真实小地图或暂时删除 |
| 端口只支持点击 | 缺少拖线预览和兼容目标高亮 | 增加拖线；保留点击方式作为键盘替代 |
| 自动布局非 DAG | 简单三列排布 | 使用拓扑分层算法 |

## 8. 优化优先级

## P0：先恢复产品真实性

1. 解决 `file://` 与正式 Web 入口混淆。
2. 重组节点库分类，合并默认 Prompt 链路。
3. 移除或禁用所有假操作与假标签。
4. 补选择、合并、批处理、抽帧、Gate 五类关键节点。
5. 将插件改成动态 NodeDefinition，不再使用固定通用插件节点。
6. 侧栏按需显示，保证画布最小可用宽度。
7. 实现真正的端口拖线、视口平移和小地图。
8. 使用 DAG 自动布局，并保持 70% 以上默认可读缩放。
9. 完整锁定设计、运行和审阅模式的写操作。

## 9. 下一版布局验收标准

- 1280 宽度下，默认节点文字和端口无需放大即可阅读。
- 进入模板后默认缩放不低于 70%，或聚焦当前任务而不是强制全图适配。
- 右侧未选择节点时不占用画布宽度。
- 节点库、Inspector 和运行抽屉可以独立收起。
- 用户可在 30 秒内找到 Prompt、图片集合、图生图、图生视频和 Gate。
- 从一个输出端口拖出后，只出现兼容节点。
- 图生视频能够明确区分首帧、尾帧和普通参考图。
- Validator 结果能够真实阻塞 Gate。
- 所有可见按钮都有结果，未实现功能不显示为可点击。
- 设计、运行、审阅模式下的可编辑范围完全不同且可预测。

## 10. 最终建议

节点库下一步应从“16 个技术节点的平铺目录”升级为三层能力模型：

1. **内置原语节点**：素材、转换、控制、校验和结果；
2. **动态插件节点**：由 Plugin/Skill Adapter 的 NodeDefinition 生成；
3. **组合模板**：文生图、图生图、文生视频、图生视频和业务工作流。

画布则应从“固定三栏的流程展示页”升级为“模式驱动的工作空间”：设计时优先编排，运行时优先状态与事件，审阅时优先媒体和证据。

在完成这两项结构调整前，不建议继续增加供应商模型、更多生成类型或后端执行接口。
