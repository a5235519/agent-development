# 多模态无限节点画布 V0.8 客观验收与后端接入决策

> 验收对象：Web Harness V0.7  
> 验收日期：2026-08-12  
> 验收目标：判断当前方案是否已经形成可理解、可完成、可恢复的产品交互，并决定哪些模块可以进入后端实现。  
> 边界：本轮不新增功能，不以页面数量或代码量代替产品成熟度。

## 1. 结论

当前版本已经从“单页画布演示”发展为覆盖工程、画布、资产、插件、运行与版本的完整 Web 工作台原型。它足以验证产品结构和核心操作，但还不适合直接连接真实模型、团队数据或正式生产任务。

建议同时使用两项成熟度，而不是用一个总分掩盖风险：

| 指标 | 评分 | 结论 |
|---|---:|---|
| 产品交互原型成熟度 | 7.2/10 | 六个核心模块均有可操作闭环，适合继续做可用性验证 |
| 后端接入准备度 | 4.8/10 | 状态源、校验一致性、资产引用、运行归档和画布性能仍有阻塞项 |

正式决策：**有条件通过交互验收，暂缓真实 Runner 与模型接入。**

可以立即进入契约化实现的部分：

- NodeDefinition、Typed Port 与 WorkflowVersion 数据契约；
- Project、WorkflowDraft、WorkflowVersion 的基础 API 设计；
- NodeRun、WorkflowRun、RunEvent 与 RunReceipt 状态模型；
- Artifact 元数据、预览和版本引用；
- PluginVersion 注册表和依赖锁结构。

必须完成 P0 整改后才能接入真实执行的部分：

- 统一工程草稿、自动保存和当前工程的状态源；
- 浏览器与服务端共用同一套完整图校验；
- 替换固定世界和全量重绘的画布实现；
- 精确到端口、角色、版本与 Hash 的资产绑定；
- 失败、取消、阻塞和成功运行的统一归档；
- Skill 转插件的人工确认、安全声明和受控发布。

## 2. 验收方法

采用任务成功率、状态可见性、错误恢复、数据一致性、可访问性和扩展风险六个维度，逐条执行以下真实任务：

1. 创建工程并切换工程；
2. 从模板或节点库搭建多模态工作流；
3. 添加、预览并绑定多张图片资产；
4. 将 Skill 分析为插件 Schema，测试并发布到节点库；
5. 运行工作流、注入故障、重试并查看 Artifact；
6. 发布工作流版本、查看运行历史并导入导出。

判定标准：

- **通过**：不依赖隐藏操作即可完成，状态和结果明确；
- **部分通过**：主流程可完成，但存在数据语义、恢复或一致性缺口；
- **不通过**：任务无法稳定完成，或界面结果可能误导真实生产。

## 5. P0 阻塞项

### P0-1：工程状态不是唯一真相源

**V0.8 整改状态：前端本地状态部分已完成，服务端并发控制仍待后端阶段完成。**

当前同时存在三个独立本地状态：

- `multimodal-canvas-harness-v07`：当前全局画布；
- `multimodal-canvas-projects-v07`：工程草稿、版本与运行；
- `multimodal-canvas-plugins-v05`：插件草稿与发布快照。

实际验证发现：切换到第二个工程后刷新页面，会重新选中第一个工程。原因是初始化始终执行 `selectedProjectId = projectRecords[0].id`。全局画布状态与当前工程草稿也可能出现错配。

整改要求：

- Project 必须成为 WorkflowDraft 的所有者；
- 持久化 `activeProjectId`；
- 取消独立的全局画布保存键，或把它降级为当前工程的缓存；
- 使用 revision/ETag 防止旧草稿覆盖新版本；
- 工程切换必须先完成保存或明确冲突处理。

已落地并验证：

- `Project.draft` 已成为画布内容的唯一持久化来源，删除独立全局画布写入；
- 新增 `activeProjectId` 持久化，刷新后恢复原工程；
- 自动保存、手动保存、新建工程和工程切换统一写入当前 `Project.draft`；
- 新建或切换工程时清理选择、撤销栈和本地运行会话，避免跨工程污染；
- 兼容迁移 V0.7 工程数据及遗留全局画布草稿，不主动删除旧键；
- 浏览器实测：工程 A 为 5 节点，工程 B 修改为 6 节点；刷新后仍为工程 B/6 节点，往返切换后两个工程节点数保持独立；控制台无错误或警告。

仍未完成：服务端 `revision/ETag`、多端冲突提示与冲突合并。这三项属于后端草稿 API 接入条件，不能由本地原型伪造完成。

### P0-2：发布校验与执行校验不一致

**V0.8 整改状态：本地共享校验内核已完成；服务端权威复验待 Runner/API 阶段接入。**

浏览器 `validateGraph()` 当前检查节点存在、端口类型和必填输入，但没有执行 CLI Validator 已具备的完整环路检查，也没有统一校验 NodeDefinition 版本、端口基数和插件依赖完整性。

风险：界面可能允许发布一个服务端拒绝或无法执行的版本。

整改要求：抽出唯一的 `graph-core` 校验包，浏览器预检、版本发布和 Runner 接收必须使用同一规则与相同错误码；服务端仍是最终权威。

已落地并验证：

- 新增无外部依赖的 `prototype/graph-core.js`，浏览器经典脚本和 Node CLI 加载同一文件；
- 画布检查、WorkflowVersion 发布、模拟运行预检、JSON 导入和 CLI 均调用 `GraphCore.validateWorkflow()`；
- 返回稳定的 `code / severity / message / nodeId / edgeId / path`，不再只返回不可定位的文本；
- 覆盖重复 ID、未知定义、位置、悬空边、未知端口、类型、端口基数、必填输入、环路、定义版本、插件 Executor 与插件依赖锁；
- V0.8 导出带插件依赖锁；V0.7 导入会补齐依赖后再使用同一内核验证；
- 14 项自动测试、CLI 验证和静态构建通过；浏览器实测非法环路导入返回 `GRAPH_CYCLE_DETECTED` 且未修改原 6 节点草稿，合法画布检查通过，控制台无错误。

仍未完成：服务端接收 WorkflowDraft/WorkflowVersion 时的权威复验与错误码透传。后端实现必须直接复用或等价封装该规则包，不允许另写一套业务判断。

### P0-3：当前画布并非真正无限且无法支撑大图

**V0.8 整改状态：第一阶段已完成，固定边界与拖动全量重绘已消除；视口虚拟化和成熟引擎迁移仍待决策。**

证据：SVG 和 `.world` 固定为 5000×3200；节点拖动的每次 pointermove 都重新执行 `renderNodes()`、`renderEdges()` 和 `renderMinimap()`。

风险：节点数量上升后发生明显卡顿；节点卡动态高度会使人工计算的端口坐标偏移；固定世界与“无限画布”产品承诺不一致。

整改要求：

- 使用成熟图引擎的数据层和视口模型；
- 节点与连线增量更新，不在拖动时全量重建；
- 端口坐标从真实 DOM/引擎锚点获得；
- 支持虚拟化、可扩展坐标和大图性能基准。

建议技术路线：React Flow / XYFlow 作为首选 Web 节点引擎；若需要自由白板、批注和复杂媒体对象，再评估 tldraw 作为外层无限画布，但不要同时维护两套图状态。

已落地并验证：

- 删除 SVG 的 `5000×3200` 固定尺寸，世界层改为 1px 原点容器加 `overflow: visible`，坐标不再受 DOM 盒子限制；
- 支持负坐标和远距离坐标，适配全图最低可缩放到 2%，网格随 pan/zoom 同步；
- 节点拖动期间只更新移动节点、相邻连线和所属分组，不调用全量 `renderNodes()` / `renderEdges()`；
- 分组拖动采用相同增量路径，缩略图更新通过 `requestAnimationFrame` 合并；
- 端口锚点优先读取真实 DOM 中心，替代依赖固定卡片高度的人工坐标；
- 新增 `npm run benchmark` 的 1000 节点/500 连线计算夹具，以及 `?benchmarkNodes=300` 的真实 DOM 夹具；基准模式不会写入工程草稿；
- 本机浏览器实测：300 节点/150 连线首次完整渲染约 80ms，单节点拖动增量约 0.20ms，完整节点和连线重绘计数均未增加；负坐标至 2.7 万单位跨度可适配到同一视口；控制台无错误。

仍未完成：

- 初次载入仍会为所有节点创建 DOM，没有按视口虚拟化；
- 主交互仍集中于单个 `main.js`，尚未形成可替换的 Canvas Adapter；
- 尚未完成 XYFlow 与当前交互契约的迁移对照实验。

因此 P0-3 不应标记为完全关闭。下一决策点应是先做 XYFlow 迁移 Spike，再决定是否继续投资自研虚拟化；不建议同时实现两套生产画布。

### P0-4：资产绑定缺少生产级引用

当前节点保存 `assetRefs` 和 `assetRoles`，但没有明确目标端口、ArtifactVersion、内容 Hash、来源、权限和生命周期。

整改要求：资产绑定统一为：

```json
{
  "targetNodeId": "generate",
  "targetPortId": "firstFrame",
  "artifactVersionId": "av_123",
  "role": "first_frame",
  "order": 0,
  "contentHash": "sha256:..."
}
```

### P0-5：运行历史只归档成功状态

当前只有 `completeRun()` 把收据写入工程历史。FAILED、BLOCKED、CANCELLED 和浏览器刷新中断没有归档，因此无法形成真实审计链。

整改要求：运行创建即持久化；每个状态变化写事件；所有终态都产生收据；客户端断线不影响 Runner 状态；重新进入工程可恢复运行现场。

### P0-6：Skill 转插件不能直接作为可信发布链路

当前分析器使用关键词判断图片、视频、脚本和 Prompt，并自动生成 `skill://` 路由。它适合解释交互，不足以理解真实 SKILL.md 的入口、依赖、权限、工具、失败语义与输出 Schema。

整改要求：

- 明确标注“AI/规则建议”，禁止一键静默发布；
- 增加人工确认 Gate；
- 解析正式 manifest，而不是只读自然语言关键词；
- 声明网络、文件、密钥、审批、模型、成本与超时权限；
- 在隔离测试 Runner 中验证后才能进入已发布插件库。

## 6. P1 优化项

| 问题 | 优化建议 |

## 8. 推荐后端接入顺序

### 阶段 A：前端域模型整改

1. 拆出 `graph-core` 和统一校验器；
2. 统一 Project → WorkflowDraft 状态树；
3. 替换画布渲染层并建立大图性能基线；
4. 定义 AssetBinding、PluginDependency 和 RunReceipt 正式 Schema；
5. 保留当前 Harness 作为回归夹具。

### 阶段 B：最小持久化后端

先实现：

- Project CRUD；
- WorkflowDraft 读取、保存与 revision 冲突；
- WorkflowVersion 发布与读取；
- PluginVersion 注册与依赖解析；
- Artifact 元数据与预签名上传；
- WorkflowRun 创建、事件流和收据读取。

此阶段仍使用 Deterministic Mock Runner，不连接真实模型。

### 阶段 C：受控 Runner

1. Runner 只接收已经发布、服务端校验通过的 WorkflowVersion；
2. 冻结 NodeDefinition、PluginVersion、ArtifactVersion 与配置 Hash；
3. 全部状态通过事件流持久化；
4. 支持幂等重试、取消、超时和失败收据；
5. 先接一个低风险图片生成 Adapter 验证闭环，再扩展视频与 Codex/Skill。

## 10. 进入真实后端前的验收门槛

以下条件全部满足后，才建议连接真实模型：

- [ ] 刷新、切换工程和多标签页下不会出现草稿错配；
- [ ] 浏览器预检与服务端发布校验输出相同错误码；
- [ ] 200 节点画布拖动、缩放和连线达到既定帧率；
- [ ] 每个必填媒体输入都能追溯到具体 ArtifactVersion 和端口角色；
- [ ] 所有运行终态都有可恢复的事件和收据；
- [ ] PluginVersion 包含权限声明、隔离测试收据和人工发布记录；
- [ ] 导入文件经过 Schema、迁移、依赖和拓扑完整校验；
- [ ] 核心编辑、发布、运行和重试路径具备自动化测试；
- [ ] 模态框、节点和端口达到基本键盘与可访问性要求；
- [ ] Harness 模拟模式与真实执行模式在界面上明确区分。

## 11. 最终建议

下一步不应继续扩充 UI 功能，也不应马上连接图片或视频模型。正确顺序是：

> 统一状态与校验 → 替换画布内核 → 固化资产/插件/运行契约 → 接最小持久化后端 → 使用 Mock Runner 验证 → 最后接真实模型。

V0.7 的价值是已经把完整产品边界暴露出来；V0.8 的目标不是推翻现有方案，而是把“可演示的完整性”转化为“可实现的可靠性”。
